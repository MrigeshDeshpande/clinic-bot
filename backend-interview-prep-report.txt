# Topic

## What was built?
A modular monolith on Next.js App Router: HTTP entrypoints under src/app/api, orchestration in src/lib, persistence in src/db/repositories, and external adapters for WhatsApp, Gemini, OpenAI Whisper, and Cloudflare R2.

## Business Problem
A single-clinic backend needed to automate patient communication, staff operations, reminders, visit closure, and payment follow-up without introducing distributed-systems-level operational overhead too early.

## Technical Problem
Avoiding a "fat route" codebase while still shipping quickly in a serverless environment.

## Solution Implemented
The project uses clear layer boundaries:
API routes -> engine/handlers -> repositories -> Neon/Postgres.
It also separates deterministic control flow from infrastructure adapters and from mutable operational state.

## Files Involved
src/lib/engine.js
src/lib/handlers.js
src/db/repositories/appointmentRepository.js
src/db/pool.js
src/app/api/webhook/whatsapp/route.js

## Tradeoffs
This is easier to ship than microservices, but the monolithic handlers.js has become a maintenance hotspot.

## Failure Modes
Boundary erosion: route handlers start embedding business logic, and the large handler module becomes a single blast radius for regressions.

## Scalability Considerations
The architecture is good for single-tenant or low-multi-tenant scale, but in-memory coordination pieces prevent clean horizontal scaling.

## Reliability Considerations
Layering helps isolate failures. Repository return values are mostly null-safe and log failures instead of throwing across the whole stack.

## Security Considerations
A modular boundary exists, but security is manually enforced route-by-route rather than via a shared secure platform layer.

## How to Explain in an Interview (2 minute version)
"I built this as a modular monolith. Routes handle HTTP concerns, the engine owns workflow orchestration, repositories isolate SQL, and adapters isolate external APIs. That gave me service-like boundaries without paying the complexity cost of separate deployables. The main lesson is that this pattern scales well organizationally until one orchestration module becomes too large, at which point I'd split workflow domains while keeping the same architectural contract."

## Possible Interview Follow-up Questions
- Why not microservices?
- Where would you split first?
- How would you enforce boundaries more strongly?

## Senior-Level Discussion Points
- This is a pragmatic modular monolith, not an accidental monolith.
- Repository and adapter boundaries are deliberate senior signals.
- The next refactor is domain decomposition, not platform explosion.

# Topic

## What was built?
A synchronous WhatsApp webhook ingestion pipeline with explicit steps: classify event, deduplicate, normalize, load session, classify intent, extract entities, handle, send reply, persist messages.

## Business Problem
Inbound patient messages must be processed exactly once or close to it, because duplicate bookings, missed replies, or out-of-order state transitions damage trust immediately.

## Technical Problem
Meta webhooks can retry, send status updates alongside messages, and run in a serverless request lifecycle that can terminate early.

## Solution Implemented
POST /api/webhook/whatsapp parses JSON once, runs migrations on cold start, and awaits processEvent(). The engine filters non-message events, skips self-messages, sorts inbound messages by timestamp, deduplicates by msg_id, and persists both user and bot messages.

## Files Involved
src/app/api/webhook/whatsapp/route.js
src/lib/engine.js
src/lib/deduplicate.js
src/db/repositories/messageRepository.js

## Tradeoffs
Processing synchronously avoids serverless background-loss issues, but increases webhook latency and couples Meta responsiveness to downstream DB/API calls.

## Failure Modes
DB outage, WhatsApp send failure, or session-save failure can still partially process a message. There is no queue or DLQ.

## Scalability Considerations
Current design is request-bound. At scale, webhook acknowledgment should be decoupled from processing through a queue.

## Reliability Considerations
The pipeline is explicit and inspectable. Deduplication is two-layered: in-memory fast path plus DB existence check.

## Security Considerations
Webhook verification token is validated on GET. POST rate limiting exists, but request authenticity is not HMAC-signed by Meta in this code.

## How to Explain in an Interview (2 minute version)
"I made the webhook pipeline explicit instead of burying logic in the route. Each stage has one responsibility: filter, dedupe, normalize, classify, mutate state, reply, persist. In serverless, I intentionally await processing before returning 200 because returning early can lose work if the platform freezes background execution. The next step for scale would be enqueue-on-ingest with at-least-once consumers."

## Possible Interview Follow-up Questions
- Why didn't you ack immediately?
- How would you add at-least-once guarantees?
- How do you handle duplicate delivery?

## Senior-Level Discussion Points
- Clean pipeline design is a strong interview story.
- Synchronous ack is a deliberate serverless tradeoff.
- The missing queue is the main reliability boundary today.

# Topic

## What was built?
A session management layer with mutable operational state, optimistic locking, in-memory cache fallback, expiration semantics, and manual-mode timeout.

## Business Problem
Conversation continuity matters more than raw message history. The system needs to remember where the patient is in the workflow and recover gracefully from transient persistence failures.

## Technical Problem
Concurrent webhook deliveries can race; DB can be unavailable; serverless instances can be cold and stateless.

## Solution Implemented
Sessions live in Postgres with a version column. saveSession() updates with WHERE version = expectedVersion, which is optimistic concurrency control. session.js also keeps a 30-minute in-memory cache for continuity and auto-flips expired sessions to ABANDONED on load. Manual mode auto-releases after 24 hours.

## Files Involved
src/lib/session.js
src/db/repositories/sessionRepository.js
src/db/migrations/001_core.sql

## Tradeoffs
Eventual consistency improves latency, but .catch(() => {}) on saves can hide persistence loss. Cache continuity helps UX but is not cross-instance.

## Failure Modes
Silent DB write failure, stale version conflicts, cache loss on restart, and inconsistent state across instances.

## Scalability Considerations
The in-memory cache does not scale horizontally. A shared cache or queue-based state machine would be needed for multi-instance correctness.

## Reliability Considerations
Optimistic locking is the key protection against clobbering concurrent session writes.

## Security Considerations
Session data is operational, not identity-bearing, but it includes patient context and should still be treated as sensitive.

## How to Explain in an Interview (2 minute version)
"I modeled sessions as mutable operational truth and message history as immutable truth. Sessions use optimistic locking because the failure mode I cared about was concurrent webhooks overwriting each other. I also added an in-memory continuity cache so transient DB failures don't immediately break the conversation, but I'd replace that with Redis if I needed true horizontal scale."

## Possible Interview Follow-up Questions
- Why optimistic locking over DB locks?
- What happens on version conflict?
- How would you make session state cross-instance?

## Senior-Level Discussion Points
- Separating mutable session truth from immutable message truth is a strong systems design signal.
- This is concurrency-aware state management, not naive chat history storage.
- The save path still has reliability debt because failures are swallowed.

## Technical Problem

## Scalability Considerations
State-machine complexity scales poorly in one file, but operational correctness scales well because behavior stays explicit.

## What was built?
A correction-aware "state repair" layer that detects "actually", "no, evening", "X instead", fragmented messages, and safe overwrite conditions.

## Business Problem
Users do not type linearly. They change their minds, send partial information, and contradict themselves mid-flow.

## Technical Problem
A simple slot-filling flow breaks when updates arrive out of order or as corrections.

## Solution Implemented
The backend adds three layers: correction-detector.js, overwrite-policy.js, and entity accumulation in entities.js. This allows progressive filling, last-write-wins during collection, explicit edit enforcement after confirmation, and correction audit metadata in session context.

## Files Involved
src/lib/correction-detector.js
src/lib/overwrite-policy.js
src/lib/entities.js
src/lib/handlers.js
docs/robustness-layer-changes.md

## Tradeoffs
This keeps the deterministic engine robust, but adds stateful mutation rules that are easy to break if not well-tested.

## Failure Modes
False-positive corrections, stale entity carryover, or allowing mutation after confirmation when edit flow should be required.

## Scalability Considerations
The design scales behaviorally better than a naive state machine because it handles chaotic input without branching explosion.

## Reliability Considerations
Mutation safety is explicit. Confirmed bookings do not silently change.

## Security Considerations
This is business-integrity security: preventing silent state corruption is effectively protecting operational correctness.

## How to Explain in an Interview (2 minute version)
"One of the strongest backend patterns here is that I separated progression from repair. Forward progression handles happy-path slot filling. Repair logic handles corrections, contradictions, and fragmented input. I then added an overwrite policy so mutation rules depend on state: in-progress fields can change, confirmed ones require explicit edit flow. That's a very interviewable example of designing for real human behavior without giving up determinism."

## Possible Interview Follow-up Questions
- Why not always let latest input win?
- How do you avoid accidental overwrites?
- How would you audit corrections?

## Senior-Level Discussion Points
- This is workflow mutation control, not just input parsing.
- The overwrite policy is a senior signal because it encodes consistency semantics by state.
- The design cleanly separates parsing, correction detection, and authorization-to-mutate.

An AI intent-classification adapter with rule fallback, confidence thresholds by risk, and shadow mode for offline comparison.

## Business Problem
The clinic wants better natural-language understanding without letting an LLM directly control production side effects.

## Technical Problem

## Solution Implemented

## Failure Modes
Quota 429s, timeout, malformed JSON, invalid intents, and low-confidence outputs.

## Scalability Considerations
Provider abstraction supports future model switching. Sampling in shadow mode controls cost.

## Reliability Considerations
High-risk intents like confirm and emergency need higher confidence thresholds, which is exactly what the code does.

## Security Considerations
The most important security boundary is decision authority: AI is advisory unless explicitly accepted.

## How to Explain in an Interview (2 minute version)
"I did not let AI directly control production behavior by default. I wrapped it behind a provider interface, timeboxed it, validated the schema, used different thresholds for high-risk intents, and added shadow mode so I could compare AI against deterministic routing without changing user-visible behavior. # Topic

## What was built?
A versioned appointment model that treats rescheduling as supersession rather than in-place mutation.

## Business Problem
Appointments are operational records. Rescheduling should preserve history and support auditability.

## Technical Problem
In-place updates destroy historical truth and make it harder to reason about concurrency and debugging.

## Solution Implemented
Appointments have logical_id, version, replaces_version, and superseded_at. Reschedules insert a new row and mark the prior version superseded. Current views use DISTINCT ON (logical_id) ordered by latest version.

## Files Involved
src/db/repositories/appointmentRepository.js
src/db/pool.js
src/db/migrations/001_core.sql
docs/truth-and-mutation-model.md

## Tradeoffs
Querying becomes more complex because every read must understand "latest version" semantics.

## Failure Modes
If readers forget DISTINCT ON (logical_id), stale rows appear. If supersession and insert are not coordinated, chains can become inconsistent.

## Scalability Considerations
Append-only version chains are usually better for audit than update-in-place, but can require archival or partitioning later.

## Reliability Considerations
This model preserves prior state even when reschedules happen under contention.

## Security Considerations
Auditability matters in healthcare-adjacent systems because mutable records can create trust and compliance issues.

## How to Explain in an Interview (2 minute version)
"I modeled appointments as immutable versions grouped by a stable logical ID. Rescheduling creates a new version instead of mutating the old one. That gave me auditability, easier reasoning about concurrency, and a clear current-vs-history query pattern. It's similar to event-sourced thinking, but implemented pragmatically with relational tables."

## Possible Interview Follow-up Questions
- Why not soft delete or a change log table?
- How do reads avoid stale versions?
- How would you archive old versions?

## Senior-Level Discussion Points
- This is a strong data-modeling story for interviews.
- It shows conscious separation of current operational state from historical truth.
- It is one of the clearest senior signals in the repository.

# Topic

## What was built?
Booking consistency controls using both application-level checks and database-enforced uniqueness.

## Business Problem
Double-booking the same slot is unacceptable in a clinic schedule.

## Technical Problem
Two requests can race: both see a slot as free, both attempt to insert.

## Solution Implemented
The database creates a partial unique index on (date, time) for status='confirmed'. The application also performs pre-checks like countAppointmentsBySlot() and "slot already booked" queries, but the DB is the real source of truth.

## Files Involved
src/db/pool.js
src/db/repositories/appointmentRepository.js
src/app/api/dashboard/appointments/route.js

## Tradeoffs
The read-before-write check improves UX, but only the unique index actually prevents races.

## Failure Modes
The dashboard quick-book route can still race between its pre-check and insert; if the DB raises a unique violation, the current route may surface a generic 500 instead of a clean conflict response.

## Scalability Considerations
DB-enforced uniqueness scales better than app-only locking in a stateless fleet.

## Reliability Considerations
Conflict prevention is delegated to the strongest layer: the database.

## Security Considerations
This is integrity, not confidentiality: preventing conflicting writes is part of system safety.

## How to Explain in an Interview (2 minute version)
"I use the database as the final arbiter of booking consistency. The app does optimistic availability checks for a good UX, but I never trust them for correctness. The partial unique index is what actually prevents double-booking. In an interview, I'd explicitly call out the gap between user-friendly checks and correctness-enforcing constraints."

## Possible Interview Follow-up Questions
- Would you use transactions or advisory locks?
- How do you map unique violations back to 409s?
- How would you support multiple chairs or providers?

## Senior-Level Discussion Points
- DB constraints are the real consistency mechanism.
- App-layer checks are advisory.
- Graceful conflict handling is the next improvement.

## Business Problem
Clinical visit records often require images, audio, or documents without permanently exposing raw storage URLs.

## Technical Problem

## Solution Implemented

## Reliability Considerations
The pipeline logs both Meta download failures and R2 failures. Media is optional, so business flow can continue even if storage is unavailable.

## Security Considerations

## How to Explain in an Interview (2 minute version)

## What was built?
A dashboard security model using HMAC-signed custom tokens, cookie auth, middleware enforcement, CSRF protection, rate limiting, body-size limits, and basic security headers.

## Business Problem
The admin dashboard mutates sensitive operational data and must be protected from brute-force, cross-site, and accidental request abuse.

## Technical Problem
Need authentication and request integrity in a lightweight deployment without a full identity platform.

## Solution Implemented
Login issues a custom HMAC token signed from DASHBOARD_PASSWORD, sets dashboard_token and csrf_token cookies, and middleware protects /dashboard and /api/dashboard. apiAuth.js adds CSRF checks for cross-origin mutations, rate limiting, and body-size guards. next.config.mjs sets CSP and other headers.

## Files Involved
src/middleware.js
src/lib/auth.js
src/lib/apiAuth.js
src/app/api/dashboard/login/route.js
next.config.mjs
src/app/api/dashboard/patients/[id]/family/route.js

## Tradeoffs
This is lighter than integrating Auth0/NextAuth, but it pushes crypto and token lifecycle responsibility into app code.

## Failure Modes
Password rotation invalidates all sessions. No key rotation or token revocation list. The family-link POST/DELETE route currently mutates data without CSRF protection, which is a real security gap.

## Scalability Considerations
Custom auth works for one admin surface, but not for multi-user RBAC, audit-friendly identity, or SSO.

## Reliability Considerations
Middleware centralizes auth checks. Rate limiting is in-memory only, so it is not reliable across instances.

## Security Considerations
Important positives: httpOnly auth cookie, SameSite, CSRF token, route middleware, CSP. Important negatives: custom JWT-like scheme, in-memory rate limiting, and missing CSRF on at least one mutating route.

## How to Explain in an Interview (2 minute version)
"I implemented a lightweight but layered security model: cookie auth in middleware, CSRF on mutations, body-size limits, and per-route rate limiting. The design is acceptable for a small private admin tool, but I would be explicit in an interview that I would not scale this custom token scheme into a multi-tenant or compliance-heavy product. The interesting part is the layered request-defense approach, not the custom crypto itself."

## Possible Interview Follow-up Questions

# Topic

## What was built?
A database access layer with retry, circuit breaker, lazy connection creation, and runtime migrations.

## Business Problem
Neon serverless and serverless runtimes can fail transiently on cold starts or network fetches.

## Technical Problem
DB calls can fail due to transport issues rather than query logic. Migrations must also happen safely across cold starts.

## Solution Implemented
pool.js wraps Neon queries with retry-on-network-failure, a circuit breaker after repeated failures, and a migrationsPromise guard so migrations run once per process. Many routes call runMigrations() defensively.

## Files Involved
src/db/pool.js
src/app/api/webhook/whatsapp/route.js
src/app/api/dashboard/appointments/route.js
src/app/api/cron/feedback/route.js

## Tradeoffs
Runtime migrations reduce operational friction but push schema management into hot paths and can increase cold-start latency.

## Failure Modes
Circuit opens and returns hard failures; migrations drift into a giant append-only script; routes call getSql() without always handling a null DB handle.

## Scalability Considerations
At larger scale, migrations should move to CI/CD or a release step, not request time.

## Reliability Considerations
Retry + circuit breaker is a serious reliability pattern for a small codebase.

## Security Considerations
Schema-at-runtime is not a direct security risk, but misconfigured env handling can create undefined behavior.

## How to Explain in an Interview (2 minute version)
"I added resilience where the real failure mode existed: serverless network/database instability. Queries retry only on network-ish failures, and after repeated failures the circuit opens to fail fast instead of thrashing. I also guarded migrations with a process-level promise to prevent repeated execution. The tradeoff is that runtime migrations are convenient but not ideal for long-term operational maturity."

## Possible Interview Follow-up Questions
- Why retry only some DB errors?
- When should the circuit open?
- When would you move migrations out of runtime?

## Senior-Level Discussion Points
- This is a real resilience mechanism, not just try/catch.
- The migration strategy is functional but fragile.
- Good interview angle: "small system with production-minded DB hardening."
